# Renderer facts

All lines cited against `76e8eec`. Re-verified independently from source (not copied from the original specification, which carried the same claims un-verified).

## Priority [I] items

**4. Is per-eye merc really just a perspective-matrix swap?**
`perspective_matrix` is uploaded as its own `glUniformMatrix4fv` call (`Merc2.cpp:908-909`), separate from the `ub_bones` UBO (bone skin matrices, `Merc2.cpp:1327`) and from the per-model light uniforms (`Merc2.cpp:1287-1303`). In `merc2.vert`, bone skinning happens first (`vtx_pos = -bones[...].X * p * ...`), lighting is computed from `rotated_nrm` (bone-space normal, no perspective involved), and only afterward is `perspective_matrix * vtx_pos` applied (`merc2.vert:58-73`). So *within this file*, swapping `perspective_matrix` per eye would not touch bone or light math — that part is settled by source alone.
What is **not** settled statically: whether the bone matrices themselves (`skel_matrix_buffer`, read from GOAL memory via `matrix_array` addresses, `Merc2.cpp:509-521`) are computed on the GOAL side relative to a single mono camera in a way baked before this C++ code ever sees them. That composition happens in GOAL/VU code outside this checkout's C++, so it can't be confirmed here.
**What would settle it:** read the GOAL-side skeleton/matrix update code (bone-to-camera-space composition, likely in `math-camera.gc`/merc bone update) to confirm bones are computed independent of any per-eye offset, or — faster — run the stereo spike: fold an eye offset into `perspective_matrix` only, leave bones/lights untouched, render both eyes, and check for correct stereo parallax with no lighting/skinning artifacts.
Status: **inferred-untestable-statically** (partially verified: uniform separation is real; the deeper bone-composition question is not).
**Stereo run (2026-09-23): verified by running it.** Folding the eye offset into the projection only (column 3 -= e * column 0, `Merc2.cpp:904-907@0ad51e600`) gives Jak the same disparity as the ground he stands on (feet 6.7 px, sand beside them 7-8 px, beach-start, 64 mm IPD, 1920 px per eye), with no lighting or skinning change between eyes. Bones need no per-eye work. See `findings/2026-09-23-stereo.md`.

**12. Can lightbench render levels without game-provided textures?**
Statically confirmed pieces: `Loader` is constructed from a `fs::path` and loads FR3 files by level name (`Loader.h:15-19`, `get_tfrag3_level`), runs its own `std::thread` (`Loader.cpp:16`, `Loader.h:52`); `TFragment::render_tree` (`TFragment.h:60`, public, no `DmaFollower` param) and `Tie3::draw_matching_draws_for_all_trees` (`Tie3.h:57`, public, no `DmaFollower` param) can be called directly; `game/graphics/gfx_test.cpp:26-33` already creates a hidden `SDL_WINDOW_HIDDEN` GL context; `runtime` is `add_library(runtime STATIC ...)` (`game/CMakeLists.txt:390`), so it's linkable into a new executable.
What is **not** settled statically: `TFragment`/`Tie3` are constructed with `const std::vector<GLuint>* anim_slot_array` — animated texture slots that, in the real game, are populated by a separate DMA/GOAL-driven texture-animation path, not baked into the FR3 file. Whether a from-disk-only lightbench renders correctly (missing only cosmetic animated textures, or something structurally more broken) can't be determined by reading source; it requires actually running it.
**What would settle it:** the lightbench spike as scoped in the original specification — build a small executable linking `runtime`, drive `Loader` + `TFragment::render_tree`/`Tie3::draw_matching_draws_for_all_trees` with a synthesized camera, and see what's missing/black (expect: static textures fine, animated-slot textures needing a stand-in).
Status: **inferred-untestable-statically** (static plumbing confirmed buildable; texture completeness needs a runtime check).

**13. Does actor culling happen on the GOAL side against one global frustum?**
Verified, with a correction to the claim's mechanism. `cull_check_all_slow` (`background_common.cpp:489`) is a C++ function used only for tfrag/tie **background BVH** culling (`TFragment.cpp:440`, `Tie3.cpp:450`) — it is not itself "actor culling". Actor/drawable visibility uses a separate GOAL function, `sphere-in-view-frustum?` (`goal_src/jak1/engine/draw/drawable.gc:48`), which reads `(-> *math-camera* plane 0..3 quad)` — the same singleton `*math-camera*` object whose planes also feed the C++ background culling path (via `add-pc-tfrag3-data`, `goal_src/jak1/engine/gfx/tfrag/tfrag.gc:271-274`, copying `*math-camera* plane 0..3` into the DMA'd `TfragPcPortData`). No per-actor or per-eye frustum instance was found anywhere in either path — `*math-camera*` is a single global.
**What would settle it further (belt and suspenders):** confirm no code ever swaps or duplicates `*math-camera*` mid-frame (e.g. for shadow/reflection passes) — a repo-wide grep for `(set! *math-camera* ...)`/local rebinds would close this out completely, but nothing found so far suggests one exists.
Status: **verified** (source alone settles the "single global frustum, GOAL-side" claim; the specific function named in the original specification was wrong).
