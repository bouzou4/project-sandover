### Priority [I] item

**8. "The bake used the `mood-lights` directions"** — i.e. the original PS2-era offline lighting bake that produced the baked palette vertex colors (`COLOR_0..7` / the mood-lights-table's per-slot data) used the *same* sun directions currently stored in `mood-lights-table` entries in `mood-tables.gc`, as opposed to some other or lost light setup.

Status: **inferred-untestable-statically**. This cannot be settled by reading engine source alone — the bake was performed by an offline PS2-era art/lighting tool whose only surviving output is the baked vertex colors themselves (via TIE/tfrag palette data, extracted through `extract_tie.cpp` / `fr3_to_gltf.cpp`, claim 5/7 above). The engine source only shows what `mood-lights-table` is used for *at runtime* (feeding `light-group 0`'s directional lights for characters, claim 2) — it has no record of, and no code path that could prove, what light setup the original bake solver actually used to produce the static per-vertex colors.

This requires the unbake experiment: fit the baked vertex colors against the `mood-lights` direction/color priors (per slot, per level) and inspect residual error. What unbake's fit-quality gate would need to show to confirm this claim:
- A per-level, per-slot linear (or low-order) fit of baked vertex color vs. `dot(vertex_normal, mood_lights[slot].direction)` (plus `amb-color`/`lgt-color` from the same table) should explain the great majority of baked-color variance — low residual, no systematic directional bias in the residual (e.g. no leftover gradient correlated with a *different* candidate direction).
- Residual should not be reducible by swapping in an alternative direction hypothesis (e.g. a coplanar/degenerate fit per Part 2 below, or a level's own bespoke override directions such as Village 3's hardcoded `mood-lights-table` overwrites, `mood.gc:1366-1393`) — if a different direction set fits materially better, that would refute the "bake used mood-lights directions" claim for that level.
- Ideally this should hold consistently across multiple levels/slots, not just one, since `mood-lights-table` values are hand-authored per level and could in principle have drifted from whatever the bake actually used on a level-by-level basis.

**Unbake result (2026-09-23): split verdict.**
- **Verified** for the day slots (0-4) of levels on `*village1-mood-lights-table*`: fit vs table 2-14° on village1, beach, jungle and finalboss, up to 18° on training. A prior-free fit recovers the same directions to within 4.4°.
- **Refuted** for the night slots 6-7 (24-43°, consistent across levels; bake vs model bias not separated) and for firecanyon slots 0/2/3, rolling and village3 (30-86°).
- **Untestable** where the bake has too little directional light to locate a sun (misty, village2, swamp, sunken, sunkenb) and on the one-slot `update-mood-quick` levels.

Details are in `sandover/kb/findings/2026-09-23-unbake-go-no-go.md` and in the Part 4 table below.

### Notable / surprising patterns (flagged per task instructions)

- **Levels with no real sun/day-night cycle at all**: `jungleb`, `maincave`, `robocave`, `lavatube`, `citadel` (and effectively `darkcave`) all bypass `update-mood-palette` and call `update-mood-quick` with a hardcoded slot-0 snapshot instead — the normal 8-slot hour-table blend simply doesn't run for these interior/cave levels. This matters for unbake: baked vertex colors for slots 1-7 (or all 8, for `darkcave`) on these levels are either driven by bespoke non-sun effects or never sampled at runtime.
- **`darkcave` has zero sun slots** — all 8 slots are driven by a bespoke `*palette-fade-controls*`-based proximity-light system (up to 7 independent nearby "torch" fades plus a fixed base), unlike any of the 5 shared effect primitives named in the original specification.
- **Village 3 hijacks the *source table*, not the slot weight** — `update-mood-village3` overwrites `mood-lights-table` data 0-3 (direction/lgt-color/amb-color) with fixed values every frame, so the "sun" slots there aren't reading the static table snapshot at all. This is a different hijack mechanism than every other level's `times[].w` weight-hijacking, and wasn't called out in the original specification.
- **`ogre` blends across three separate full mood-context globals** (`*ogre-mood*`, `*ogre2-mood*`, `*ogre3-mood*`) by camera distance, rather than hijacking slots within a single context — a level-composition pattern unique to `ogre`/`finalboss` (which does something structurally similar with `*finalboss2-mood*`).
- **`sunken` discards its own `update-mood-palette` light-group output** — after computing the normal sun snapshot, it immediately overwrites `light-group 0`'s dir0/dir1/dir2/ambi with hardcoded colors lerped by camera depth, so the mood-lights direction/color for that level's "sun" slots never actually reaches the character light kit.
- **`*palette-fade-controls*`** (an external control-input array, not part of the 5 named primitives) drives `times[]` slots directly on `sunken` (slot 3), `maincave` (slots 1-2), `lavatube` (slot 2), `finalboss` (slot 2), and `citadel` (slot 3), plus almost all of `darkcave`. This is a recurring 6th "primitive" the original specification's worklist didn't name.
