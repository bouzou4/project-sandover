# Water optimization pass: near ocean rim, world map lookup on water (2026-10-10)

Items 7 and 8 of "(a) Invisible wins" in `2026-10-10-perf-profile.md`. Both are exact: no
pixel can change. Measured at 3840x2160, MSAA 2 (the #390 default, both arms), every Sandover
row at its top tier, HDR PQ, perf-max.yaml spots with the 180 s neighbour wait (ok at every
spot in every run).

## Item 7: near ocean rim (CPU)

`CommonOceanRenderer::near_rim_on_plane` marks the near ocean's rim vertices (edges its
textured pass uses once), which take the flat plane where the mid ocean meets them (#305 fix).
It rebuilt a nested `std::unordered_map` of every edge, keyed by GS position, every frame.

Mechanism of the fix: the rim depends only on the index list and on which vertices share a GS
x, y (the position classes). Each frame computes the classes in one flat open-addressing
table; when they and the index list equal the last frame's, the previous rim is reused.
Otherwise the edges are counted in a second flat table instead of the nested maps. The output
(`pad[1]` per vertex) is the same function of the same inputs; an offline test against the old
code (random strips with shared, split and merged positions, 3600 comparisons) found no
difference.

The cache does not always hit with a still camera: the rebuild rate (counter
`ocean-rim-rebuilt`) is 0 at village1-waterfront, 0.14-0.18 at the beach spots, 0.33-0.41 at
beach-shore and 0.96 at open-sea-low, so the game's near ocean index list or position classes
change from frame to frame there (likely its wave heights moving vertices across the clip or
the strip skip bits). The flat-table rebuild is what makes those spots cheaper.

New counters (render thread, `PERF-CNT`): `ocean-near-cpu-ms` (the near ocean's water setup,
rim included), `ocean-rim-cpu-ms` (the rim alone), `ocean-rim-rebuilt`.

## Item 8: world map lookup on water

`water_shade` (`ocean_common.frag`) calls `wsg_sun_vis` -> `ws_water_vis` once per lit water
pixel. Two findings:

- The cascade box test already runs before any tap: `ws_sun_vis_c` returns 1 with
  `covered = false` before `ws_vis_cascade` when no cascade box holds the point, and when the
  day fade or the cascade count is 0. Nothing to add there.
- The lookup's result `open` reaches the colour only through terms that are all 0 when the
  sun elevation factor `up` is 0, the analytic glint's radiance is 0 (sun below its horizon or
  facing away) and the reflection's sun glow `pow(dot(R, L), 24)` is 0. `water_shade` now
  computes the glint radiance and the glow first and skips the lookup when all three are 0.
  `up` alone was not enough: the glint and the glow are not scaled by `up`.

At the measured spots the sun is up wherever the map is drawn (the map fades out with the
sun's disc below 0.03), so the gate does not fire and the GPU cost is unchanged; it saves the
lookup only in the dawn and dusk hand-over where the water's blended sun direction is below
the horizon while the map still draws. The lookup's own cost (`water-map` probe: shadow option
34 off) is 0.2-2.2 ms per spot; taking a share of it needs a look change (a cheaper kernel on
water or a coarser map for it), which is a plan item for the maintainer, not this pass.

paused A/B is the proof.

## Measurement trap (cause not established)

Branch runs from a worktree project root made by the rig-capture recipe of the time (game/,
presets, out/jak1, goal_src, custom_assets, decompiler) timed about 1.5 ms slower than the main
checkout at every spot, in `actor-shadows` and `tfrag`, spots without water included (runs
`opt-water-*-m2d`/`m2e`/`m2f`). `SANDOVER_DATA` was set to the main checkout's data folder in
all of them. After the root was re-synced (game/ mirrored from the rebased worktree, out/jak1
refreshed from the main checkout, which copied changed files) and `sandover/data/lighting`,
`sky` and `materials` were added, the branch timed level with the base (runs `opt-water-*-g*`).
gk reads those three folders from `$SANDOVER_DATA` first and from the project root only when
the variable is unset, so they are not the cause. Hypotheses, untested: a stale `out/jak1` in
the root (game code older than the goalc build the rig ran), or files present in the main
checkout's `game/` but not tracked by git, which a copy of the worktree's `game/` lacks.
Compare a branch root against the main checkout at an untouched spot before trusting its
timings.
