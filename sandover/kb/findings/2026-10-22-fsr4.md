## Answer (≤5 lines)
FSR 4 (AMD FSR SDK 2.3.0, ffx-api, signed DLLs; the driver serves provider 4.1.2) runs as engine
mode 3 on a D3D12 device on the GL adapter, bridged to GL by a D3D11On12 device and
WGL_NV_DX_interop2 with no cross-API fence. At 50 % (1080p to 4K) against native MSAA 8x it beats
FSR 3.1: FLIP still 0.0437 vs 0.0530, pan 0.0386 vs 0.0432. Cost: dispatch 1.66 ms on the queue,
frame +2.2 ms over FSR 3.1 (the interop hand-over stalls the render thread). Fallbacks verified.

- Releases [V] (REPO releases): FSR 4 ships in the 2.x line ("AMD FSR SDK" from 2.1).
  v2.0.0 (2025-08-20) FSR 4.0.2; v2.1.0 (2025-12-10) 4.0.3 and the mandatory
  `ffxCreateContextDescUpscaleVersion`; v2.2.0 (2026-03-23) 4.1.0; v2.3.0 (2026-06-24, commit
  `60f4ea81909200d8542eca14dccb2628b763a9a3`) 4.1.1, the latest, adding RDNA 3 discrete GPUs.
- Source [V]: closed. `Kits/FidelityFX/docs/techniques/super-resolution-ml.md`: "AMD FSR Upscaling
  4 requires integration using the AMD FSR API and use of the signed binary distribution". The tree
  carries FSR 2/3 source only. FSR 3.1 in this engine stays the GL compute port of SDK 1.1.4.
- API [V] (`Kits/FidelityFX/docs/getting-started/ffx-api.md`): ffx-api, five C entry points
  (`ffxCreateContext`, `ffxDestroyContext`, `ffxConfigure`, `ffxQuery`, `ffxDispatch`) over
  `pNext`-chained descriptors. From SDK 2.0 the app loads `amd_fidelityfx_loader_dx12.dll` (26 KB),
  which loads `amd_fidelityfx_upscaler_dx12.dll` (27 MB, FSR 4, 3 and 2 providers). "This can be
  loaded at runtime with LoadLibrary and GetProcAddress (this is recommended)":
  `ffx_api_loader.h` fills a function table. Headers: `Kits/FidelityFX/api/include/{ffx_api.h,
  ffx_api_types.h, ffx_api_loader.h, dx12/ffx_api_dx12.h}`, `Kits/FidelityFX/upscalers/include/
  ffx_upscale.h`.
- Version selection [V]: `ffxQueryDescGetVersions` (with `ffxCreateBackendDX12Desc` chained, else
  `FFX_API_RETURN_NO_PROVIDER`) lists the providers the DLL offers on this device; `ffxOverrideVersion`
  picks one at create; `ffxQueryGetProviderVersion` names the live one. The docs say not to
  hard-code version ids, only to pick by the returned name/version.
- Backend [V]: D3D12 only. No Vulkan backend in any release ("Vulkan is currently not supported in
  SDK", only `backend/dx12` in the tree). [E] OptiScaler reaches FSR 4 from Vulkan through its own
  D3D12 bridge, which is the shape used here from GL.
- Hardware gate [V]: v2.0.0 docs "FSR4 requires an AMD 9000 series GPU or later"; v2.3.0 "an AMD
  7000 series discrete GPU or AMD 9000 series GPU or later". GPUOpen: "When running on other
  hardware the AMD FidelityFX API will automatically select ... 3.1.5". No "is supported" query
  exists: support is read from the version list and the live provider version. [E] RDNA 3 needs
  Adrenalin 26.6.2 or later (INT8 path). [I] NVIDIA and Intel get 3.1.5 from the DLL; the engine
  then reports FSR 4 unavailable, since its own GL FSR 3.1 already covers that.
- Inputs [V] (`super-resolution-ml.md`, `ffx_upscale.h`): the same `ffxDispatchDescUpscale` as FSR
  3.1 (colour, depth, motion vectors, exposure, reactive, transparency and composition, output,
  jitter, motion vector scale, render and upscale size, sharpening, frame time in ms, pre-exposure,
  reset, camera near/far/vertical FOV, view-to-metres). FSR 4 specifics: reactive and T&C masks are
  not required (`ffxQueryDescUpscaleGetResourceRequirements`); colour should be linear; inputs in
  `D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE`; Shader Model 6.6; exposure R32_FLOAT 1x1;
  inverted depth strongly recommended; a NativeAA (1.0x) preset; about 318 MB VRAM and 1.32 ms at
  4K on RDNA 4 (AMD's table).
- Licence [V] (`docs/license.md` at v2.3.0): a binary-only AMD licence applies "to all files
  except as noted below"; the exception list (845 paths, including
  `Kits\FidelityFX\signedbin\amd_fidelityfx_loader_dx12.dll` and `...upscaler_dx12.dll`, lines

  Inc. ... Permission is hereby granted, free of charge ... to deal in the Software without
  restriction ... The above copyright notice and this permission notice shall be included in all
  copies or substantial portions of the Software."). v2.0.0's licence is plain MIT. The
  integration guide adds that apps "must use one of the provided signed DLLs" (no rebuilt or
  modified DLL). [I] Shipping both DLLs with the MIT notice is allowed; to stay inside the stricter
  reading of the binary-only header as well, the DLLs are used unmodified and the notice ships beside
  them.
- Distribution [V]: the DLLs are plain git blobs (not LFS) in `Kits/FidelityFX/signedbin/`, so
  `raw.githubusercontent.com/.../<commit>/Kits/FidelityFX/signedbin/<dll>` is a stable,
  hash-pinnable URL. Fetched at configure with a SHA-256 per file like the DLSS SDK
  (`third-party/amd-fsr4/fetch.cmake`), not committed (27 MB of binary in the repository is the
  only reason; the licence would allow it). [V] GPUOpen: drivers "can update the version of FSR 4
  Upscaling used in-game"; [I] keep AMD's DLL names unchanged so the driver recognises them.

## 2. Design as built

### D3D12 container (`D3d12Bridge.h`, commit `c36a30785`)
Design decision (2026-10-22): D3D12 is the one DirectX container for every vendor feature; D3D11
survives only as the GL bridge (WGL_NV_DX_interop2 takes D3D10/11 devices only).
- Device: `D3D12CreateDevice` at feature level 12_0 on the adapter whose LUID the GL context
  reports (`GL_EXT_memory_object_win32`, `glGetUnsignedBytevEXT(GL_DEVICE_LUID_EXT)`,
  `IDXGIFactory4::EnumAdapterByLuid`); no LUID, no device. One direct queue, one fence, a ring of
  three allocators and lists, a timestamp query heap.
- Bridge: `D3D11On12CreateDevice` on the same queue, opened with `wglDXOpenDeviceNV`. Verified on
  the AMD driver before writing it (standalone probe, scratch): the interop accepts the D3D11On12
  device; a D3D12 committed resource wrapped with `CreateWrappedResource` registers and moves data
  both ways; ordering holds with no CPU wait and no explicit fence (GL writes seen by a D3D12 copy
  submitted right after the hand-over; a D3D12 clear queued behind 400 8K clears seen by GL's next
  read). A plain D3D11 device and an NT-handle-shared D3D11 texture also register (the fallback
  shape, not needed).
- API (render thread only):
  - `get()`, `init()` (one log line and full teardown on any failure), `available()`, `status()`.
  - `acquire()` / `release()` / `release_if_unused()`: features hold the device; the renderer
    calls `release_if_unused()` after the startup probes, so a machine where nothing can use it
    keeps no D3D12 device. `shutdown()`.
  - `device()`, `queue()`, `adapter()`, `d3d11()` (the D3D11On12 device).
  - `begin_commands()` -> a reset list from the ring (waits for that slot's fence);
    `submit(list)` -> executes and signals, returns the fence value; `last_signal()`,
    `completed()`, `wait_cpu(v)`.
  - `create_shared(tex, w, h, dxgi_format, d3d12_flags, gl_access, name)` /
    `destroy_shared(tex)`: a D3D12 committed resource (state COMMON between hand-overs), its
    D3D11On12 wrapper and a GL texture name; locked for GL on return.
  - `to_d3d12(list, n)`: unlock for GL, release the wrapped resources, flush D3D11On12 onto the
    queue; D3D12 work submitted after it follows GL's commands. `to_gl(list, n)`: acquire and
    lock; GL's next commands follow the queue's work so far.
  - `make_timer()`, `timer_begin/end(id, list)`, `timer_ms(id)`: queue timestamps read a few
    frames late.
  - Rows: D3D row 0 is the top of the image; the bridge does not flip, callers copy flipped.

### FSR 4 (`Fsr4Upscaler.h`)
- Runtime: `amd_fidelityfx_loader_dx12.dll` loaded with `LoadLibraryExW` from gk's folder, the
  five ffx entry points by `GetProcAddress` (gk imports nothing from it).
- Startup (`probe`): the bridge must be up; load the runtime; `ffxQueryDescGetVersions` with the
  DX12 backend chained; the newest provider whose name parses to 4.x or later is picked and pinned
  with `ffxOverrideVersion` on every create (AMD: never hard-code ids). None -> unavailable, the
  bridge is released. A 64x64 -> 128x128 test context of it, and `ffxQueryGetProviderVersion` on
  it, then run on a worker thread (the first context in a process takes 4-11 s on a cold driver cache, see 3); a
  live provider below 4 withdraws the mode (`poll()` each frame), `run()` waits for it.
- Per frame, at FSR 3.1's place (end of the sprite bucket): GL input pass (one MRT draw, rows
  flipped: colour as is, D24S8 depth to R32F, RG16F velocity) into shared textures -> `to_d3d12`
  -> list: inputs COMMON -> NON_PIXEL_SHADER_RESOURCE (AMD's required state), output COMMON ->
  UNORDERED_ACCESS, `ffxDispatch`, back to COMMON -> `submit` -> `to_gl` -> flipped blit into
  the display target (depth and stencil for the text buckets).
- Context: `maxRenderSize` = render size, `maxUpscaleSize` = display size; recreated (and reset)
  on a size or format change. Flags `DEPTH_INVERTED`, `DEPTH_INFINITE` (the clip matrix has
  `k1` = -1.000038: an infinite far plane) and `NON_LINEAR_COLORSPACE`, dispatch flag
  `NON_LINEAR_COLOR_SRGB`: the scene buffer is sRGB-encoded (FP16 headroom above 1), and FSR 4
  wants linear colour or to be told (measured in 3; FSR 3.1 and DLSS take it as HDR or LDR).
- Inputs as FSR 3.1/DLSS: jitter `(jx, -jy)` (rows flipped; `pc-set-aa 7` negates an axis), the
  shared Halton sequence and phase count (`scene_jitter`), motion vector scale `(1, -1)`, exposure
  a 1x1 R32F of 1, pre-exposure 1, frame time in ms, reset on `!frame_valid`, no velocity or a
  new context; camera near `k0 / (1 - k1)` from the clip matrix (`w_k0`, `w_k1`), far unused
  (infinite), vertical FOV from `tan_half_y`, view-to-metres 1/4096 (as FSR 3.1); sharpening = FSR 3.1's sharpness (0.8). No reactive or
  T&C mask: the context's resource requirements report required 0xf (colour, depth, motion
  vectors, exposure), optional 0.
- Fallback: no D3D12 device, no runtime, no 4.x provider, the warm-up context not FSR 4, a context
  or dispatch failure -> `g_fsr4_supported` false, `fsr3_on()` true for mode 3: FSR 3.1 runs.

## 3. Proof (rig, 2026-10-22)
One instance (`--parallel 1`), solo on the GPU, 4K output, render scale 50 % (1920x1080),
`--play-look`, village1 fountain camera from `shots/fsr3-stills.yaml`, actors frozen, no
particles, wind or time-of-day effects. Manifest `shots/fsr4-spike.yaml`; data
`$SANDOVER_DATA/shots/fsr4-spike/` (`probe/`, `run1/` first build, `sign/`, `variants/`, `run2/`
final build, `fb-nodll/`, `fb-nod3d12/`, crop sheets `run1/crops-still.png`,
`crops-variants.png`). The branch build ran from a staged root (`rig-capture.md`, "branch
builds") with the worktree's `goal_src` compiled into it: the main checkout's compiled GOAL
belongs to a newer branch and calls engine options master's gk does not have (boot stalls).

- Probe frame (`probe/`): `d3d12: D3D12 device on <adapter> (the GL context's adapter),
  D3D11On12 bridge`, `fsr4: upscaler providers on this device: 4.1.2 *, 4.1.1, 3.1.5, 2.3.4`
  (the driver adds 4.1.2 over the DLL's 4.1.1), `fsr4: context 1920x1080 -> 3840x2160 ...,
  provider 4.1.2 *, resources required 0xf`; image upright and complete.
- Jitter sign (`sign/`, still, FLIP against MSAA 8x): as built `(jx, -jy)` 0.0574; x negated
  0.0884, y negated 0.0959, both 0.1047.
- Colour and sharpening (`variants/`, still): colour as FSR 3.1 (HDR flag) 0.0578; told
  sRGB-encoded 0.0443 (kept, visibly closest to the reference); sharpness 0 0.0498, 1.0 0.0549
  (the default 0.8 is FSR 3.1's and stays shared). Native 100 %: FSR 4 0.0422, FSR 3.1 0.0343
  (both against MSAA 8x; sharpening and AA style dominate at native).
- Final build (`run2/`), FLIP LDR mean against native MSAA 8x at the same camera (pan: each of
  the 12 burst frames against the reference burst, yaw 0.5 deg per frame; reference burst from
  `run1/`, as run2's reference shot hit a `RIG:CAMERA` timeout; it does not involve FSR):

  | 50 % | still | pan mean | pan last 4 |
  |---|---|---|---|
  | FSR 3.1 | 0.0530 | 0.0432 | 0.0415 |
  | FSR 4 | **0.0437** | **0.0386** | **0.0380** |

  Repeatability: FSR 3.1's still against the reference 0.0533 (run1) vs 0.0530 (run2).
- GPU time (PERF windows of 60 frames over the shots, medians, first window dropped):

  | | FSR 3.1 | FSR 4 |
  |---|---|---|
  | upscale on its API (GL `fsr3`; `fsr4-d3d-ms` queue timestamps) | 0.98 ms | 1.66 ms |
  | GL span of the pass (`fsr4` = inputs 0.04 + dispatch span 2.86 + output 0.23) | 0.98 ms | 3.13 ms |
  | frame (GPU) | 18.5 ms | 20.7 ms |
  | render thread in the interop calls (`fsr4-sync-cpu-ms`) | | 16.6 ms |

  Split of the CPU time (log every 600 frames): hand-over (unlock, release, D3D11On12 flush)
  13-14.6 ms, record and submit 0.05 ms, hand-back (acquire, lock) 2.0-2.4 ms. The hand-over
  waits for GL's frame so far to finish and the hand-back for the dispatch; the GPU gap the GL
  span shows (3.13 - 1.66 = about 1.5 ms) is that round trip.
- Startup: runtime load and provider query 125 ms on the render thread; the first context in
  the process takes 4-11 s on a cold driver cache (11.4 s and 4 s seen) and 57-62 ms warm, so
  it runs on a worker thread; the first FSR 4 frame waits for it if it is still running.
- Fallbacks (`fb-*`, mode 3 requested by the shot):
  - no runtime DLL beside gk: `fsr4: unavailable (no amd_fidelityfx_loader_dx12.dll beside
    gk)`, `d3d12: no feature uses the device; torn down`, `fsr3: targets ...`: FSR 3.1 ran;
  - no D3D12 device (`SANDOVER_D3D12_OFF=1`): `d3d12: unavailable (SANDOVER_D3D12_OFF=1)`, no
    FSR 4 probe, FSR 3.1 ran;
  - a runtime without a 4.x provider (other vendors, RDNA 2): the same unload and release path as
    the missing DLL (code read; no such GPU on the rig);
  - both fallback images complete (mean 80.0 against 80.2 for FSR 3.1 in run2).

## 4. Open issues
- Interop sync cost (the main one): the WGL interop's unlock blocks the render thread until GL
  has finished the frame so far (13-14.6 ms) and the lock until the dispatch is done (2.3 ms);
  frame +2.2 ms against FSR 3.1 at 50 %. Lever: `GL_EXT_memory_object_win32` +
  `GL_EXT_semaphore_win32` (both exposed by this driver) importing the D3D12 resources and the
  D3D12 fence into GL directly, so GL and the queue wait on each other on the GPU
  (`glSignalSemaphoreEXT` / `glWaitSemaphoreEXT` with fence values). It changes the bridge, not
  FSR 4; worth doing before the DLSS port lands on the same bridge.
  Tried 2026-10-23: blocked by the AMD GL driver (`2026-10-23-bridge-semaphores.md`).
- `w` units: FSR 3.1 and FSR 4 both take the clip `w` of the motion-vector pass as game units
  (view-to-metres 1/4096); `k0` = 0.0727 makes the near plane 0.036 units, which suggests the
  clip `w` is not in game units. Shared with FSR 3.1; affects only FSR's metre-based thresholds.
- HDR output: the colour is passed as sRGB-encoded with FP16 headroom above 1; the sRGB flag's
  handling of values above 1 is not documented. Shots here are SDR captures of the HDR target;
  an HDR10 look check at a bright scene is the next step.
- No reactive mask: FSR 4 reports it optional (none required); the sprite HUD is reconstructed
  with the scene, as with DLSS. The HUD split stays shared with FSR 3.1 and DLSS.
- RDNA 3 (FSR 4.1 INT8 path, Adrenalin 26.6.2+), NVIDIA and Intel were not run: no such GPU on
  the rig.
- The DLSS port to the D3D12 container is a separate PR.
