## Answer (5 lines)
The long freezes are first-use work on the render thread, not game logic. On the AMD GL driver
the first draw of each program in a new state builds a pipeline (0.6-3.5 s per renderer cold),
and the driver keeps that cache per executable path, so every newly staged binary starts cold.
The first lit frame after the boot load took 12.2 s: pipeline builds plus the blocking load
(2.6 s) and the material maps (2.8 s). In VR that was 12 s without a frame reaching the runtime.

## What the GPU, driver and code do
| Cost | Where it lands | Cold size |
|---|---|---|
| Driver pipeline build, per program and render state, on its first draw | the group that drew (`cpu-merc`, `cpu-ocean-mid`, vista passes), or the next sync when the GPU waits (`cpu-emlights-track`, the tile-light readback; `cpu-present-swap`) | 0.6-3.5 s per renderer |
| Driver cache keyed by executable path | a second run of the same binary copy: 5.9 s -> 1.3 s at boot; a byte-identical copy in another folder is cold again | - |
| Blackout load (`Loader::update_blocking`) | the frame the blackout ends: every level's upload in one frame | 2.6 s |
| Material maps of levels loaded before PBR turned on | decoded and uploaded in the first frame that draws them (`hitch-pbr-ms`) | 2.8 s |
| FSR 3.1 programs | built on the first upscaled frame | 1.0-1.4 s |
| FSR 4 first frame | `cpu-fsr4` in boot frame 3; the context itself is 60 ms (`hitch-upscaler-ms`), the rest is the first dispatch | 4.3 s |
| HDR presenter's first HDR10 present | `cpu-present-encode` in boot frame 2 (the SDR 640x480 swapchain replaced by HDR10 3840x2160) | 3.3 s |

`SANDOVER_HITCH_FINISH=1` (a `glFinish` per group) moves each wait into the group that caused it.
In XR one render-loop iteration is one OpenXR frame, so each of these is a frame the runtime never
gets.

## Fix
- XR keep-alive thread (`OpenXr.cpp`), experimental and off by default
  (`SANDOVER_XR_KEEPALIVE=1` turns it on): when nothing reached the runtime for 150 ms, it ends
  the render thread's begun frame with no layers and then submits empty frames at the display
  rate (xrWaitFrame paces it) until the render thread begins a frame again; that frame's late end
  is dropped. A failed xrBeginFrame stops the empty frames until the render thread is back. The
  keep-alive's calls and the render thread's xrWaitFrame, xrBeginFrame, image release and
  xrEndFrame share one mutex; image acquire and wait run outside it, and the thread is joined
  before xrEndSession. The runtime gets black frames instead of a freeze. It is off by default
  because `XR_KHR_opengl_enable` expects the frame calls on the thread that owns the session's GL
  context, and this one calls xrBeginFrame/xrEndFrame from a second thread while the render
  thread holds it; it has run on the emulated session only.
- Pre-roll (`OpenGLRenderer::preroll_step`): when a level finished loading during the blackout,
  the frames after it are drawn as usual but presented black until 3 frames in a row come in
  under max(50 ms, 1.5x the median of the last 32 lit frames before the blackout), at most
  500 ms of wall time past the first black frame (that one carries the load's first draws), so
  the pipeline builds, the map uploads and the loader's first frames happen under the loading
  screen. A blackout that loads nothing (a respawn) has none.
- The world shadow caster and min-max programs and the actor shadow occupancy program are built
  at renderer start. FSR 3.1's programs are not: building both variants at start cost 1-2 s on
  every run, vanilla included; the upscaler setting arrives from the game's settings push in the
  first boot frames, before any level draws, and the variant in use builds there on first enable,
  as before. The min-max pass's vertex array is created on its own check, not with the program
  (built early, it stayed 0, the bounds pass drew nothing and the sun shadows read stale bounds:
  village1 scene-linear mean 0.43 instead of 0.79).

| flat, saved profile | village1-hut | 31 ms, 0 | 31 ms, 0 |

Each submit gap over 50 ms after the change is the onset of a stall (the 150 ms allowance before
the first empty frame); once bridged, empty frames go out every 11 ms. The beach frame of
74-219 ms comes 40-50 s after the load on both builds (tile-light readback waiting on a first
draw), not at the load. The 12 lit frames of 50-71 ms in village1 seen in an earlier XR run were
contention: that run shared the GPU with another game instance and used the first keep-alive
pacing (150 ms between empty frames); solo, neither build has any.

Five minutes in village1 and across to the beach (Jak moved between four spawn points every
30 s, flat, effects from the launcher forms): no pre-roll during play (the two activations are
the warp's blackout load before it), 6 lit frames over 50 ms: 9.3 s and 0.75 s when the
launcher's effect forms landed 0.3 s after the pre-roll had ended (the effects' first draws:
`cpu-emlights-track` 8.2 s), 0.69-0.78 s three times on the first move into the beach area
(streamed, no blackout), and one of 61 ms.

Pre-roll after the review changes (load-only trigger, wall-time cap, relative calm), flat,
cold copies, one game instance: the boot load still gets a pre-roll (2 black frames, 9.6 s: the
11.5 s first frame and the 0.63 s frame after it, ended by the cap); the warp to village1-hut
right after boot, a second warp to village1-hut and the warp to the beach (all levels already
resident through the neighbours) log `pre-roll: none, the blackout loaded no level`. Render
thread time (present excluded; during these runs the 4K monitor was off the desktop and every
present waited about 250 ms, so frame intervals are not comparable): longest lit frame at boot
3.8 s (boot frame 3, FSR 4, as before), village1 lit frames over 50 ms 0, both cases. No FSR 3.1
program build at start with FSR 4 saved.

## Follow-ups
- Effects turned on outside a blackout still freeze flat play on first use (9.3 s above). XR
  freezes too by default; with `SANDOVER_XR_KEEPALIVE=1` the keep-alive sends black frames.
  Options: build the pipelines by drawing every renderer's programs off screen behind the boot
  load, or start the pre-roll when an effect setting turns on.
- Boot frames 2 and 3 (before the boot level load, no level drawn yet): the HDR presenter's first
  HDR10 present 3.3-3.4 s and FSR 4's first dispatch 4.3 s, cold. Moving them off the render
  thread or behind a boot screen needs a presenter and FSR 4 warm-up path.
- First moves into a newly streamed area: 0.7-0.8 s frames (no blackout to hide them).
- Confirm the keep-alive on the real SteamVR session (empty `xrEndFrame` from a second thread)
  before it goes on by default. The design that stays inside `XR_KHR_opengl_enable` is pumping
  from the render thread: split the long first-use work (pipeline warm-up, the blocking load,
  map uploads) into slices and end an empty frame between slices on the thread that owns the
  context, so no second thread touches the session.
- For that SteamVR run: after a keeper `xrBeginFrame` failure, one waited-but-never-begun frame
  is outstanding when the render thread next calls `xrWaitFrame`.
- Re-measure frame intervals with the monitor on (the review re-run had 250 ms presents).
- Upload material maps in the loader when PBR turns on after a load.
