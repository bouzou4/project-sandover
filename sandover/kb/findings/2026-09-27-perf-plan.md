# DRAFT: frame cost, where it goes and what to do about it (2026-09-27 baseline)

> **Draft.** Based on the 2026-09-27 baseline only. Optimization runs last: re-profile once the
> rendering work is done (local-light shadows and the fixes in flight will add cost and may
> change the passes below), then revise this plan before any optimization lands.

Source: `$SANDOVER_DATA/perf/20260927-1613/` (build `04c79e359` + the timer scopes of the frame profiler):
14 spots, 3840x2160, MSAA 4, FP16 target, toon tonemap, HDR10 DXGI present, every effect on,
vsync off. Every spot is GPU-bound; frame 7.8 ms (finalboss) to 22.4 ms (beach-shore).
Marginals in that run come from one window per state; the single-window noise is about
±2 ms, so a marginal under ~2 ms is a direction, not a number. The A/B/A tool in `sandover-perf` fixes that
for the next run.

Categories: **(a)** invisible by construction (same pixels, or differences far below 1/255);
**(b)** very likely invisible, needs a capture diff; **(c)** a visible trade-off, a decision
decides.

## Reading the numbers

- `buckets` contains `ssao`, `emissive-lights`, `bloom`, `vista` and `water-depth`. With SSAO
  off `buckets` drops 3-6.5 ms, and `ssao` + `emissive-lights` explain nearly all of it
  (maincave: 6.42 = 2.74 + 3.73). The "geometry gets slower with SSAO on" hypothesis is
  mostly refuted: the rest is 0-1.2 ms per spot (normal/emissive MRT writes, target clears,
  and the sync effect below).
- GL timestamp spans also count the GPU idling while the CPU has not issued the next command.
  The tile lights read their candidate row back with a blocking `glReadPixels` mid-frame, which
  drains the GPU queue every frame. After the drain the CPU is barely ahead of the GPU, so CPU
  latency shows up as GPU time in the groups that follow: `present` (dx interop lock, D3D copy,
  Present) and the first geometry groups of the next frame. With the tile lights off, `present`
  gets 0.4-1.75 ms cheaper and `tfrag` 0.2-0.7 ms cheaper at the outdoor spots. That is part of
  the tile-light cost, although no tile-light pass runs in those groups.
- **Negative savings for `hdr-output` / `hdr-target`**: both switch the present path from
  the DXGI flip-model chain to `SDL_GL_SwapWindow`. A windowed GL swap is a blit-model present:
  the driver copies the 4K back buffer into the DWM redirection surface and DWM composes it,
  which costs 1-3.5 ms of GPU time in `present` (1.6-3.5 ms measured vs 0.25-1.9 ms on the DXGI
  path). So `hdr-output` off costs more, and `hdr-target`'s real saving is its bucket drop
  (0.75-4 ms) minus that present penalty. The DXGI path is the cheaper present even for SDR;
  See spatial audio.
- In `darkcave` with SSAO off, `present` grows by 4.5 ms and the frame only drops 0.7 ms: once
  the GPU work is small, the frame is paced by something else (CPU/EE or present back-pressure
  with `SetMaximumFrameLatency(1)`), so the GPU-bound label only holds with everything on.

## Heavy items

### 1. Tile lights: 3-4.7 ms frame (emissive-lights scope 1.3-3.7 ms)

Mechanism (`EmissiveLights.cpp`, `emissive_light.frag`):
1. resolve: a 4K MSAA 4 RGBA16F blit to a single-sample copy (~8 x 33 MB traffic);
2. tiles: 64x36 fragments, each walking its 60x60 px tile at every second pixel (900 taps,
   csz + emissive + colour fetches). Only 2304 threads for the whole GPU, so it runs at a few
   percent occupancy, latency-bound;
3. select + **blocking readback** of 64 candidates, CPU tracking, texture uploads;
4. light pass: every opaque pixel at 4K fetches 4 normal samples, 4 emissive samples, colour and
   depth, then for each of up to 32 tile lights and 32 world lights does two `texelFetch`es
   (up to ~128 fetches per pixel x 8.3 M pixels), even where no light is in range.

| Candidate | Saving (est.) | Class |
|---|---|---|
| **Light lists as uniforms** instead of 1-D textures (same float bits), and **skip pixels no light reaches** (a range pre-check mirroring the loop's tests; the loop would add exactly 0) | 0.8-2 ms | (a), prototyped (parked) |
| **Read the candidates back a frame late** (PBO + fence, converted with that frame's camera) | 0.5-2 ms (the `present` bubble and early-frame starvation) | (b), prototyped (parked): identical on a static frame; in motion new lights appear one frame later behind the existing 2-frame hysteresis |
| Tiles pass as a two-level reduction (e.g. 8x8 partial sums, then per tile) | 0.2-0.5 ms (measure `emlights-tiles` first) | (a)/(b): float summation order only |
| Light pass: per-tile light lists (cull lights per 64-px tile on the CPU or in the select pass), so each pixel loops only its tile's lights | further 0.3-1 ms | (a) |
| Drop the resolve blit: read the MSAA colour directly (average in-shader) in tiles and light passes | 0.2-0.4 ms | (b): resolve vs in-shader average rounding |
| Tile lights at half resolution (light pass at 1/4 pixels, bilateral upsample) | 1-2 ms | (c): softer light edges on geometry |

### 2. SSAO itself: ~1.7 ms (SSAO marginal minus tile lights; ssao scope 1.35-2.74 ms)

Mechanism (`SsaoRenderer.cpp`): full-res MSAA depth copy, linearize (min of 4 samples) and a mip
chain, AO at half resolution (bestPairNormal + N taps), two blur passes, then a full-res
composite drawn twice (background, characters; stencil-selected) that multiplies the MSAA
colour and reads 4 emissive samples per pixel. The normal target (RGB10A2 MSAA 4) and
emissive mask (RG8 MSAA 4) are extra MRT writes in every opaque geometry pass.

| Candidate | Saving (est.) | Class |
|---|---|---|
| **Composite skips pixels whose AO is exactly 1** (multiplying by 1.0 is a no-op; the emissive and luma-floor terms cannot move it) | 0.1-0.5 ms | (a), prototyped (parked) |
| Depth copy + linearize: linearize straight from the render framebuffer's depth texture instead of blitting it first | 0.1-0.3 ms | (a) needs the depth attachment as a texture |
| One composite pass reading the stencil bit through a stencil texture view (GL 4.3) | 0.1-0.2 ms | (a) |
| Fewer AO taps or quarter-resolution AO | 0.3-1 ms | (c) |

### 3. Vista neighbours: 4-10 ms at outdoor spots (open-sea-low 9.6)

Mechanism (`VistaRenderer.cpp`): every resident outdoor neighbour level (up to 6 at beach-shore)
draws its full tfrag/TIE/shrub at `lod_tfrag`, frustum culling only, no occlusion, after the
game's own opaque buckets. PBR shading makes vista pixels 1-1.9 ms more expensive and the FP16
target 0.3-2.4 ms (bandwidth: overdraw of hills behind hills). The ocean over the vista (`ocean-mid`)
also gets 1 ms more expensive with the vista drawn.

| Candidate | Saving (est.) | Class |
|---|---|---|
| Draw neighbours nearest first (sort `todo` by distance to each level's bounds), so early-z rejects hidden far terrain | 0.5-2 ms | (b): only ties at equal depth can change |
| Occlusion culling per tree node against the main level's depth (hi-Z or occlusion queries from the previous frame) | 1-4 ms | (b): conservative tests are exact; query latency can pop for one frame |
| Skip the normal/emissive MRT writes for vista draws if nothing reads them there | 0.2-0.6 ms | (b): check SSAO/tile lights on the far hills |
| Lower LOD (the tfrag low-res trees, TIE low LODs) past a distance | 2-5 ms | (c) |
| Cheaper shading (no PBR / no envmap) for neighbours past a distance | 1-2 ms | (c) |

### 4. Water: up to 5.8 ms (open-sea-low, mostly `ocean-mid` 5.3 ms)

Mechanism (`ocean_water.tesc`, `Materials.cpp`): within 250 m every mid-ocean edge is cut into
0.75 m world segments (up to 64 per edge) so it meets the near grid without cracks; beyond that 3
GS pixels per segment. A low camera over open sea sees 250 m of water at grazing angles, where
0.75 m segments are far below a pixel in the vertical: many sub-pixel triangles, poor quad
utilisation at MSAA 4, and the envmap pass tessellates the same way. Water depth copy
0.1-0.9 ms.

| Candidate | Saving (est.) | Class |
|---|---|---|
| Within 250 m, cap the level by the pixel criterion too (coarser of 0.75 m and N px) outside the near-grid seam band | 1-3 ms at low sea cameras | (b): wave silhouettes where segments are sub-pixel |
| Share one tessellation for the textured and envmap passes (transform feedback or one pass writing both terms) | 0.5-1.5 ms | (a) |
| `water-depth` 0.75 ms at open-sea only: find why a depth blit costs 6x more there (depth decompression after the ocean?) | 0.5 ms | (a) after diagnosis |

### 5. PBR: 1-2.7 ms

Per-pixel material shading on tfrag/TIE/vista. Candidates: skip the PBR path for pixels of
class "plain" (branch on material) (a); half-rate envmap sampling (c). Measure per class first.

### 6. HDR target (FP16): 0.8-4 ms of bucket time (net 0.5-2.7 after the present swap)

RGBA16F MSAA 4 doubles colour bandwidth vs RGBA8 in every pass. R11G11B10F MSAA would halve it
but loses destination alpha, which PS2 blending reads: not possible without moving alpha
elsewhere (c, large). Keep.

### 7. Present: 0.25-1.9 ms (DXGI), 1.6-3.5 ms (GL swap)

| Candidate | Saving (est.) | Class |
|---|---|---|
| Write the PQ encode straight from the pcrtc pass into the interop texture (one 4K pass less) | 0.1-0.3 ms | (a) if the encode math is kept |
| Double-buffer the interop texture so the GL draw never waits for last frame's D3D copy | 0-0.5 ms | (a) |
| Use the DXGI flip-model present for SDR output too (scRGB or 8-bit), not the GL swap | 1-2 ms in SDR | (a) for the image; a platform change |

### 8. Bloom, shadows, fur: < 1 ms each

Bloom resolves the frame a second time right after the tile lights' resolve (0.2-0.4 ms, (b)
if shared: bloom must then read the pre-light colour, a visible change, or the lights' own
output). Shadows 0.2-2 ms (temple-top 1.95): not looked at yet. Fur is noise.

## Parked prototype (branch `perf/easy-wins`, from master `eebb896df`; unbuilt, unmeasured)

Written before the "optimize last" rule was restated; kept as a starting point, to be rebased
and re-checked after the re-profile. All three default on, `(pc-set-perf-opt MASK)` bits 1, 2, 4:

1. **Tile-light readback a frame late** (bit 1): candidate row into a pixel buffer with a fence,
   read on the next frame and converted with that frame's camera. No CPU-GPU drain.
2. **Tile-light loop from uniforms + skip unreachable pixels** (bit 2): the light and world
   lists go in as uniform arrays (identical floats); pixels no light reaches are discarded
   before the normal, emissive and colour fetches.
3. **AO composite skips AO = 1** (bit 4): `dst * 1.0` is `dst`, so those pixels are discarded.

New GPU sub-scopes for the next run: `ssao-depth-lin`, `ssao-ao`, `ssao-blur`,
`ssao-composite` (in `ssao`) and `emlights-resolve`, `emlights-tiles`, `emlights-track`,
`emlights-light` (in `emissive-lights`). `sandover-perf --toggles opt-...` switches each
optimization off as an A/B/A marginal (negative = what it saves); `python -m
sandover.rig.pixdiff A B` reports the per-shot max channel difference of two capture runs.

Verification when it is picked up (about 10 min): `sandover-perf --bin <copy> --only
village1-night jungle maincave --frames 90 --toggles opt-all opt-light-readback opt-light-loop
opt-ao-skip`, then the same three spots captured twice from `shots/perf.yaml` with the play
defaults after load (`sandover-settings-reset!` + `sandover-settings-reapply`), once with
`(pc-set-perf-opt 0)` and once with `7`, and `pixdiff` on the two runs: pass = max channel
difference <= 2 on every shot.
