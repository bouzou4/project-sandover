## Answer (≤5 lines)
DLSS super resolution (SDK 310.9.1, NGX D3D11 API, no Streamline) is the second temporal upscaler:
Upscaler row value 1 (`dlss`, engine mode 2) beside Temporal AA (FSR 3.1, the default). It runs on
a D3D11 device on the GL context's adapter, on textures shared through WGL_NV_DX_interop2, at FSR
3.1's place with its inputs; the render scale keeps its exact percent and picks the NGX mode whose
range contains it (100 % is DLAA). No DLL ships; where none is found, FSR 3.1 runs instead.

## Remaining steps
- Cost: measured in the combined perf pass after merge. The GPU timers `dlss`, `dlss-inputs`,
  `dlss-eval`, `dlss-output` and the counters `dlss-d3d-ms`, `dlss-sync-cpu-ms` stay for it.
- Mip bias and a linear-colour input (see Open items), shared with FSR 3.1.
- The sprite HUD split, shared with FSR 3.1 (see Pipeline and HUD).
- Rigs without an NVIDIA GPU cannot run DLSS: there it is always unavailable and FSR 3.1 runs.

Done:
- Bring your own DLL: the package never ships `nvngx_dlss.dll` or a licence file
  (`NOT_SHIPPED` in `package.py`, tested). gk imports no NGX or DLSS DLL (`llvm-objdump -p`).
- Resolution order (`findings/2026-10-19-dlss-dll-resolution.md`):
  1. `nvngx_dlss.dll` beside gk.
  2. Otherwise NGX `PathListInfo` points at the folder of the newest plain `nvngx_dlss.dll` under
     `%ProgramData%/NVIDIA/NGX/models/dlss_override/versions/*/files/*/`, the NVIDIA App's
     override cache (NVIDIA-signed DLLs; newer versions there are `.bin` files NGX cannot use).
  3. Otherwise DLSS is unavailable, with one line naming what was tried, and FSR 3.1 runs.
- NGX init and the capability query run at startup (`DlssUpscaler::probe`, about 1 s), so
  `(pc-get-aa-available 1)` reflects the runtime state. `NVSDK_NGX_UpdateFeature` runs on a
  detached thread. `SANDOVER_DLSS_NO_STORE=1` skips step 2 (diagnostic).
- Resolution tests (village1, 4K):

  | Case | Result |
  |---|---|
  | No DLL anywhere (`SANDOVER_DLSS_NO_STORE=1`) | NGX init ok, super sampling unavailable (`0xbad00004`, feature not found); one warn line, AA-AVAIL 0, the game ran on the fallback |
  | No DLL beside gk, override cache | `PathListInfo` on the cache folder (`nvngx_dlss.dll` 310.2.1.0, NVIDIA signature valid); DLAA feature created, AA-AVAIL 1 |
  | DLL beside gk (310.9.1) | feature created, AA-AVAIL 1 |

- Black output: the input pass `texelFetch`ed scene textures that have mipmap filters and no
  mips, which returns zero; it now binds a NEAREST sampler.
- Jitter sign: static camera, 4 frames per sign, frame-to-frame difference of the output on
  static pixels (display-encoded MAE x 255): default (`(jx, -jy)`) 0.16, x negated 0.18,
  y negated 0.27. The default is kept; `(pc-set-aa 6 n)` remains as a diagnostic.
- Pan (camera pan, 8 frames, previous frame warped by the velocity, static pixels, MAE x 255,
  input -> DLSS output): DLAA 2.01 -> 0.63, 67 % 4.52 -> 1.23, 50 % 4.57 -> 1.61.
- Live session on an NVIDIA rig: DLSS judged better than FSR 3.1, no ghosting found; the HUD was
  captured at DLAA, 67, 50 and 33 %.

## Licence verdict
Source: NVIDIA RTX SDKs License (v. March 14, 2024) with the NVIDIA RTX Supplement, `LICENSE.txt`
at https://github.com/NVIDIA/DLSS/blob/v310.9.1/LICENSE.txt (same text on `main`).
- (a) Committing the headers and the import library to this repository (public): **not allowed**.
  Section 1(c) grants distribution of SDK materials only "as incorporated in object code format
  into a software application"; section 4(b) forbids copying or distributing any portion otherwise.
  Headers in source form and a standalone `.lib` in a public repository are neither.
- (b) Shipping `nvngx_dlss.dll` in the release zip: permitted by 1(c) as object code distributed
  with the application, but only together with the licence's conditions on that distribution
  (2(c) terms at least as protective, supplement 1 NVIDIA GPUs only) and the supplement's
  obligations on applications that incorporate the SDK (NVIDIA marks and attribution, 7.1(b) and
  7.2(c); notice before a commercial release, 4). The release does not take those on: it does
  not ship the DLL or the licence file and carries no NVIDIA branding. That reading is the reason
  the DLL is not shipped.
- What is built: `third-party/nvidia-dlss/fetch.cmake` downloads the six headers,
  `nvsdk_ngx_d.lib` (dynamic CRT) and `nvngx_dlss.dll` from the pinned tag with a SHA-256 per file
  into the build tree (or reads `SANDOVER_DLSS_SDK_DIR` offline); `gk` links the library. The
  library is NGX's loader: gk's import table has no NGX or DLSS entry (checked with
  `llvm-objdump -p`), and the DLL is only opened at run time once the startup check found it. The
  build copies the DLL beside `gk.exe` in the build tree for local runs; staging copies it with the
  other DLLs; `sandover-package` never ships `nvngx_dlss.dll` or `NVIDIA-DLSS-LICENSE.txt`
  (`NOT_SHIPPED`, tested). A configure without network builds without DLSS (stub, unavailable).
- Bring your own: players put `nvngx_dlss.dll` in the mod folder next to `gk.exe` (from the DLSS
  SDK on GitHub or an installed game that uses DLSS); the zip README's requirements and the
  repository README's settings say so. Without it, and without a copy in the NVIDIA App's
  override cache, the startup check logs one `dlss: unavailable (...)` line,
  `(pc-get-aa-available 1)` is 0 for that run and FSR 3.1 is used; it is evaluated at every start.

## Bridge
- Device: `D3D11CreateDevice` on the adapter whose LUID the GL context reports
  (`GL_EXT_memory_object_win32`, `glGetUnsignedBytevEXT(GL_DEVICE_LUID_EXT)`), else the first
  NVIDIA adapter. One device of our own, separate from the HDR presenter's (both live on the same
  adapter on a single-GPU machine; the HDR one follows the monitor).
- NGX: `NVSDK_NGX_D3D11_Init_with_ProjectID` (custom engine, a fixed GUID-like project id, data
  path `<user misc dir>/ngx`, NGX file logging off), capability parameters,
  `SuperSampling.Available` checked; `FreeMemOnReleaseFeature` on.
- Shared textures (D3D11 storage, GL names through `wglDXRegisterObjectNV`): colour
  (render size, RGBA16F with the FP16 scene, else RGBA8), depth (R32F), velocity (RG16F), all
  `RENDER_TARGET | SHADER_RESOURCE`, registered write-discard; output (display size, the colour
  format, `UNORDERED_ACCESS | SHADER_RESOURCE`), registered read-only. Exposure is a D3D-only 1x1
  R32F of 1. If the driver refuses to share a UAV texture, DLSS writes a D3D-only UAV texture and a
  `CopyResource` moves it into a shareable one (logged `output copied`).
- Formats: DLSS reads colour in any format, motion vectors as RG16F or RG32F, depth as any
  one-channel or depth format (programming guide 3.3). Interop shares D3D-owned storage, so the
  renderer's own textures are copied in any case; the D24S8 depth goes to R32F (a colour target
  the input pass can write), colour and velocity keep their formats, all in one pass.
- Input pass: one full-screen draw into the three shared textures (MRT), `texelFetch` with the rows
  flipped so D3D's row 0 is the top of the frame (DLSS sees it upright).
- Output: a `glBlitFramebuffer` with the destination rows reversed from the shared output into the
  display target (a GL texture with depth and stencil for the text buckets, as FSR 3's).

## Sync
All shared objects stay locked for GL (`wglDXLockObjectsNV`) except around the evaluate:
input pass (GL) -> `wglDXUnlockObjectsNV` (hands them to D3D after GL's commands on them) ->
evaluate (+ copy when needed) -> `ID3D11DeviceContext::Flush` -> `wglDXLockObjectsNV` (hands them
back after D3D's commands) -> output blit (GL). The extension orders the two APIs' work on the
locked objects; no explicit fence. Cost is measured, not assumed: the GL timestamp span `dlss-eval`
covers unlock, evaluate and lock as GL's queue sees them, the counter `dlss-d3d-ms` is the evaluate
alone on the D3D device (timestamp queries, read a few frames late), and `dlss-sync-cpu-ms` the
render thread's time in unlock, submission and lock. Interop overhead = `dlss-eval` minus
`dlss-d3d-ms` (GPU) and `dlss-sync-cpu-ms` (CPU).

## Input mapping
| DLSS input | Renderer source | Notes |
|---|---|---|
| colour | scene colour at the sprite bucket's end, render size, 1 sample (as FSR 3) | display-encoded; FP16 scene: `IsHDR`, exposure texture 1, pre-exposure 1; else LDR (0..1) |
| depth | scene depth-stencil texture, same moment, copied to R32F | GEQUAL cleared to 0: `DepthInverted` |
| motion vectors | `MotionVectors` RG16F velocity, render size, rows flipped | `p_prev - p_cur` px, +y up in GL; after the flip +y must point down: `InMVScale (1, -1)`; `MVLowRes`, not `MVJittered` |
| jitter | `scene_jitter` Halton (2, 3), shared with FSR 3 | `InJitterOffset = (jx, -jy)`: the projection's content offset in render pixels, DLSS's MV axes (guide 3.7.3); `(pc-set-aa 6 n)` negates an axis (diagnostic) |
| phase count | `scene_jitter::phase_count` = 8 x (display / render)^2, shared with FSR 3 | DLSS guide table: 8 DLAA, 18 quality (1.5x), 32 performance (2x) |
| reset | `!MotionVectors::frame_valid()`, no velocity, a new feature | cuts, load blackout, resize, first frame |
| frame time | render-thread frame interval (FSR 3's clock) | `InFrameTimeDeltaInMsec` |
| sharpness | none | deprecated in this SDK |
| bias current colour, transparency masks | none | the guide says not to use the bias mask with current models |

Modes (`quality_for`): render/display width 1 -> DLAA; >= 0.6 -> quality (77 % is inside its
dynamic range; a render width outside the range NGX reports is logged); >= 0.45 -> performance;
below -> ultra performance. Presets pinned to the SDK's own defaults: K for DLAA, quality and
balanced, M for performance, L for ultra performance (`DLSS.Hint.Render.Preset.*`), so a driver
default change does not move the look.

## Pipeline and HUD
Identical to FSR 3 (`findings/2026-10-18-fsr3.md`): scene, SSAO, tile lights, bloom and sprites at
render size, the velocity pass, DLSS at the end of the sprite bucket, the debug, HUD text and
subtitle buckets at display size into the DLSS display target, tonemap and HDR encode in the final
pass. HUD: text is drawn after DLSS at display size (sharp in every mode); the sprite HUD is drawn
in the sprite bucket with the scene, so it is jittered and reconstructed with it. FSR 3 marks it
reactive with its autogen mask; DLSS has no equivalent input for current models, so a HUD sprite
over a moving background may trail; no trailing was reported in the live session. The HUD split
is a follow-up shared with FSR 3.1. Off in stereo and XR (`m_render_state.stereo_active`), like FSR 3.

## Fallback
`DlssUpscaler::context_supported()` and `probe()` at renderer start (Jak 1): WGL_NV_DX_interop2
entry points, an NVIDIA adapter behind the context, NGX init with the DLL found as above, and the
super sampling capability. The result is `Gfx::g_dlss_supported`, exposed to GOAL as
`(pc-get-aa-available 1)`; the Upscaler row offers DLSS only when it is 1. A later device, feature
or evaluate failure clears it. Wherever DLSS is selected but unavailable, FSR 3.1 runs instead
(from the next frame after a runtime failure); where FSR 3.1 cannot run either (below GL 4.3), the
MSAA path. A build without the SDK compiles a stub that reports unavailable.

## Open items
- Colour is display-encoded, not linear; HDR mode with exposure 1 follows the FSR 3 choice. If the
  smoke run shows exposure-related ghosting, a linear copy (inverse of the display encode) in the
  input pass is the lever.
- Mip bias: DLSS asks for a negative texture LOD bias below native (guide 3.5); FSR 3 does not
  apply one either. A shared follow-up for both temporal modes.
