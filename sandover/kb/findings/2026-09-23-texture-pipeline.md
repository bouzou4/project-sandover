## Answer (<=5 lines)
ComfyUI over chaiNNer: its `/prompt` API takes the full workflow JSON per call, so a script parameterizes every node input per run natively; chaiNNer's CLI `--override` flag (added since the original limitation was documented) now does support per-run overrides for text/number/file/directory inputs, so the premise that it cannot is outdated, but dropdown/checkbox inputs still can't be overridden and CLI mode is still explicitly experimental. spandrel is a safe MIT loader, but the actual upscale weights are the real license risk — OpenModelDB tracks per-model licenses and many community ESRGAN/DAT/SwinIR checkpoints are non-commercial or unlicensed; spandrel itself only ships permissive-license architectures in the base package. DeepBump (GPL, ONNX, CPU-capable) is a clean keep for normal maps. The diffusion-based intrinsic-decomposition models (Marigold-IID, RGB<->X, Material Palette) are all defer-or-drop: too slow or license-gray for thousands of small textures. RGB<->X's weights are under an Adobe Research "noncommercial research purposes only" license, not a standard SPDX license, and are a real risk to flag.

## Implications for the design
- Standardize the runner on ComfyUI: build one API-format workflow JSON per operation (upscale, normal-derive, channel-split) and drive it from a Python script that edits node `inputs` fields and POSTs to `/prompt`; poll via the history/WebSocket API for completion. This avoids chaiNNer's dropdown-input override gap entirely.
- Before first run, disable ComfyUI Desktop telemetry in Settings (do not assume default-off), pre-populate `models/` with every checkpoint the workflow needs, and disable ComfyUI-Manager's "check for updates on startup" — all game textures stay local this way with no incidental network calls.
- Treat every upscale-model weight file as its own license decision, not a bundled assumption of spandrel's MIT status: check the OpenModelDB entry (or equivalent source) for each `.pth`/`.safetensors` before adding it to the pipeline's model set, and keep a per-model license log alongside the pipeline config.
- Use DeepBump's CLI directly (subprocess or in-process ONNX Runtime call) as the normal-map stage; it is small, GPL-licensed, CPU-capable as a fallback, and already scriptable without a GUI.
- Do not build the material-channel-split stage around Marigold-IID, RGB<->X, or Material Palette for the initial pipeline. RGB<->X is dropped outright on license grounds (research-only license text, VRAM right at the card's limit). Marigold-IID and Material Palette are deferred pending a small offline latency/throughput pilot (Marigold-IID: per-image diffusion cost across thousands of small textures; Material Palette: per-material-class LoRA training cost before any batch inference) — neither fits a simple "run over a directory" model without additional pipeline stages.
- For material channel splitting in the near term, prefer simpler non-diffusion heuristics or hand-authored rules per material class over any of the four intrinsic-decomposition options evaluated, until one of the deferred models clears a pilot.

## Follow-ups
- Run a timed pilot of Marigold-IID at 4 steps/ensemble=1 on a representative batch of the actual small textures (32-512px) to get real throughput and VRAM numbers on the target 12 GB GPU, since published figures are for larger/benchmark resolutions.
- Confirm RGB<->X's actual VRAM footprint on the target 12 GB GPU with a batch of small textures before deciding whether "minimum 12GB" leaves any practical headroom; if it does not fit cleanly, this reinforces the drop verdict independent of the license issue.
- Build the per-checkpoint OpenModelDB license log before pulling any specific ESRGAN/DAT/SwinIR weight into the pipeline.
- Re-check whether a future chaiNNer release adds `--override` support for Dropdown inputs, which would close the remaining CLI parameterization gap.
