> Editorial note (2026-09-23, post-ADR-0004): the VR scope decision dropped eye tracking,
> gaze and PSVR2Toolkit entirely (stereo 3D via OpenXR + SteamVR only, gamepad input
> unchanged). The gaze/PSVR2Toolkit findings below are kept as a record of the evaluation;
> treat them as refuted/moot, not as a plan item. The OpenXR/SteamVR/GL-binding findings
> still stand.

## Answer (<=5 lines)
Vendor the OpenXR-SDK (Apache-2.0) loader/headers; it is active and current as of 2026-09-21. SteamVR still exposes `XR_KHR_opengl_enable` natively on Windows (added 2020, still listed 2026-09) — no deprecation found, but keep a D3D11+interop fallback path as contingency against known SteamVR OpenXR swapchain-copy overhead. Gaze is available over standard OpenXR today: SteamVR's runtime supports `XR_EXT_eye_gaze_interaction` since v2.8 (Oct 2024), and PSVR2Toolkit (MIT, active) has fed PSVR2 gaze into that SteamVR extension since its own v0.1.3 (Sept 2025) — so the engine can consume gaze via `XR_EXT_eye_gaze_interaction` without binding to the toolkit's own DLL/IPC API. The toolkit's native CAPI still exists as a secondary/experimental path for richer raw data.

## Evidence
- OpenXR-SDK license Apache-2.0, pushed 2026-09-21, latest release `release-1.1.63` (2026-09-02): https://github.com/KhronosGroup/OpenXR-SDK, https://github.com/KhronosGroup/OpenXR-SDK-Source/blob/main/LICENSE
- OpenXR-SDK-Source is for building the loader from source/codegen; OpenXR-SDK ships pregenerated headers/loader — the artifact to vendor in-tree: https://github.com/KhronosGroup/OpenXR-SDK, https://github.com/KhronosGroup/OpenXR-SDK-Source
- `OpenXR.Loader` NuGet package (Apache-2.0) exists as an alternative prebuilt Win32/UWP artifact: https://www.nuget.org/packages/OpenXR.Loader/
- SteamVR added native `XR_KHR_opengl_enable` support on Windows and Linux, confirmed by Valve's "Programmer Joe" on 2020-06-23: https://steamcommunity.com/app/250820/discussions/8/2448217320134601817/
- SteamVR's own OpenXR extension-support list currently shows `XR_KHR_opengl_enable`, `XR_KHR_D3D11_enable`, `XR_KHR_D3D12_enable`, `XR_KHR_vulkan_enable`/`enable2` as supported: https://steamcommunity.com/app/250820/discussions/8/3121550424355682585/
- SteamVR 2.17 shipped to stable 2026-09-10, confirming the runtime is under active development going into the Steam Frame launch: https://vr.org/articles/steamvr-2-17-stable-32-bit-openxr-runtime-2026
- SteamVR OpenXR compositor swapchain-copy overhead (ignores `XR_SWAPCHAIN_USAGE_UNORDERED_ACCESS_BIT`, forces extra copy pass) — general compositor behavior, not GL-specific: `inferred` from community report, no Valve primary confirmation found: https://steamcommunity.com/app/250820/discussions/0/7056649947875504398/
- OpenGL swapchain-format workaround needed for SteamVR (`GL_RGBA8`/`GL_SRGB8_ALPHA8`), with partial upstream fix noted for `GL_DEPTH_COMPONENT32F` in a SteamVR beta: https://github.com/godotengine/godot/pull/71708
- SteamVR's OpenXR runtime supports `XR_EXT_eye_gaze_interaction` since SteamVR 2.8 (Oct 2024); the public driver-side API for third-party drivers to feed eye-tracking data into it landed in SteamVR 2.12: https://community.khronos.org/t/xr-ext-eye-gaze-interaction-questions/111300
- PSVR2Toolkit repo: MIT license, description "Unofficial modification for the official PlayStation VR2 driver/app... to improve your PlayStation VR2 experience on PC": https://github.com/BnuuySolutions/PSVR2Toolkit
- PSVR2Toolkit README states the toolkit and its eye-tracking data are "intended for NON-COMMERCIAL use only," separate from the MIT LICENSE file's permissive grant: https://github.com/BnuuySolutions/PSVR2Toolkit
- PSVR2Toolkit v0.1.3 (2025-09-15) changelog: "Implemented SteamVR eye tracking for OpenXR applications," explicitly replacing the need for a third-party OpenXR eye-tracker shim: https://github.com/BnuuySolutions/PSVR2Toolkit/releases
- PSVR2Toolkit release history and dates (v0.1.0 2025-08-14 through v1.0.0-experimental-2 2026-09-13): https://github.com/BnuuySolutions/PSVR2Toolkit/releases
- PSVR2Toolkit CAPI is WIP; `psvr2_toolkit_capi.dll` ships with a shared-memory component and IPC object names are suffixed with a layout generation, so mismatched builds silently fail: `inferred` (community/PR discussion, not an official specification): https://github.com/BnuuySolutions/PSVR2Toolkit/pull/49
- Virtual Desktop's VDXR is a separate OpenXR runtime that bypasses SteamVR for ~10% performance gain, but it targets Quest/Pico-class devices over Virtual Desktop's own streaming path, not PSVR2 via the Sony PC adapter — not applicable to this use case: https://www.uploadvr.com/virtual-desktops-vdxr-runtime/
- Monado is Khronos-conformant and supports GL/D3D11/D3D12, but on Windows it's limited to simulated devices for headsets without a Monado-native driver; PSVR2 support is Linux-oriented (`monado-psvr2` driver work): https://monado.freedesktop.org/, https://github.com/DMJC/monado-psvr2

## Implications for the design
- Vendor the OpenXR-SDK loader/headers in-tree per the upstream project's existing third-party-vendoring convention; this is a clean Apache-2.0 drop-in with no build-system surprises beyond adding it to the existing vendor tree.
- Design the graphics backend so GL rendering targets an OpenXR swapchain via `XR_KHR_opengl_enable` as the primary path, but keep the D3D11 submission path (`WGL_NV_DX_interop2`/`GL_EXT_memory_object_win32` share, `XR_KHR_D3D11_enable`) as a documented, buildable fallback — not because GL support is deprecated, but because SteamVR's OpenXR compositor has known copy overhead that should be benchmarked on the actual 12 GB NVIDIA GPU before committing.
- Moot: gaze-directed rendering and any PSVR2Toolkit integration are out of scope per ADR-0004. Input stays
  gamepad-only; no eye-tracking transport is needed.
- Do not vendor or redistribute any Sony driver component or PSVR2Toolkit binaries; the project has no
  dependency on PSVR2Toolkit at all going forward.
- HUD-as-OpenXR-quad-layer plan is compatible with either the GL or D3D11 graphics binding, since quad layers are submitted through the same `xrEndFrame` composition layer path regardless of the enabled graphics API.

## Follow-ups
- Benchmark GL-direct vs. D3D11-interop submission on the actual target GPU once the OpenXR loader is wired up, to decide whether the SteamVR swapchain-copy overhead is acceptable for this engine's frame budget.
- Moot: PSVR2Toolkit and OpenXR gaze are out of scope per ADR-0004; no further follow-up needed on either.
