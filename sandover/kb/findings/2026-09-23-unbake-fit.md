## Answer (<=5 lines)
Keep all three, but change the decomposition: don't call `scipy.optimize.least_squares` once over millions of palette entries. Split the fit — a small dense nonlinear outer solve over the ~8 global light parameters (good fit for `least_squares`), and a closed-form bounded linear inner solve per entry (`scipy.optimize.lsq_linear`/`nnls`, vectorized), with PyTorch as the GPU batching fallback if the vectorized CPU inner loop is too slow. For clustering, `sklearn.cluster.HDBSCAN` (built into scikit-learn since 1.3) is a better default than manual-`eps` DBSCAN for point-light candidates from effect-slot residuals; MeanShift is fine only if residual sample counts per level stay small.

## Evidence
- scipy.optimize.least_squares is BSD-3-Clause, latest release v1.18.1 published 2026-08-21, repo pushed 2026-09-23, ~15k stars: https://github.com/scipy/scipy
- `least_squares` accepts a callable `jac` for an analytic Jacobian (or finite differences), supports sparse Jacobians (csr array or `LinearOperator`) and `jac_sparsity` for finite-difference sparsity patterns, which forces the `lsmr` trust-region solver; `lm` does not support sparse Jacobians; `exact` solver is "suitable for not very large problems with dense Jacobian matrices" while `lsmr` is for "sparse and large Jacobian matrices"; `x_scale` rescales variables so trust-region steps have comparable effect per dimension; robust losses `linear`/`soft_l1`/`huber`/`cauchy`/`arctan` via `loss` and `f_scale`; methods `trf` (bound-constrained trust region reflective) and `dogbox` (rectangular trust region, Powell dogleg): https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.least_squares.html
- `scipy.optimize.lsq_linear` solves bounded linear least squares (`trf` or `bvls` methods), with bounds as `(lb, ub)` arrays or scalars: https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.lsq_linear.html
- PyTorch repo is BSD-3-Clause per its LICENSE file (GitHub API reports `NOASSERTION` for the auto-detected repo license field, but the actual LICENSE text is BSD-3-Clause): https://github.com/pytorch/pytorch/blob/main/LICENSE
- PyTorch latest release v2.14.0 published 2026-09-02, repo pushed 2026-09-23, ~103k stars: https://github.com/pytorch/pytorch
- PyPI carries CPU-only wheels for Windows and macOS; CUDA wheels are served from `download.pytorch.org/whl/cuXXX` (cu118, cu126, cu128, cu130) and must be selected explicitly on Windows: https://docs.astral.sh/uv/guides/integration/pytorch/
- uv pins a CUDA-specific PyTorch index via `[[tool.uv.index]]` (with `explicit = true`) plus `[tool.uv.sources]` mapping `torch`/`torchvision` to that index (optionally scoped with a `sys_platform == 'win32'` marker), or via `uv pip install torch --torch-backend=auto` / `UV_TORCH_BACKEND=auto`, which detects the installed CUDA driver and picks the matching index: https://docs.astral.sh/uv/guides/integration/pytorch/
- `torch.linalg.lstsq` supports batched matrices (leading batch dims on both `A` and `B`), but on CUDA the only valid driver is `gels`, which assumes `A` is full rank — rank-deficient batches either silently misbehave (non-batched) or raise `_LinAlgError` (batched); CPU offers `gelsy`/`gelsd`/`gelss` drivers that handle rank-deficient input: https://docs.pytorch.org/docs/stable/generated/torch.linalg.lstsq.html and https://github.com/pytorch/pytorch/issues/117122
- scikit-learn is BSD-3-Clause, latest release 1.9.1 published 2026-09-11, repo pushed 2026-09-22, ~67k stars: https://github.com/scikit-learn/scikit-learn
- `sklearn.cluster.HDBSCAN` has been part of scikit-learn since version 1.3 (no separate `hdbscan` package required): https://scikit-learn.org/1.5/whats_new/v1.4.html and https://scikit-learn.org/stable/modules/generated/sklearn.cluster.HDBSCAN.html
- scikit-learn's clustering docs state DBSCAN assumes globally homogeneous density and its `eps` parameter is hard to tune, while HDBSCAN "alleviates this assumption and explores all possible density scales" using the more robust `min_samples` hyperparameter, and is multithreaded with better runtime complexity than OPTICS at the cost of worse memory scaling: https://scikit-learn.org/stable/modules/clustering.html
- MeanShift complexity is documented as tending toward `O(T*n*log(n))` in low dimensions and `O(T*n^2)` in higher dimensions, and `estimate_bandwidth` is "much less scalable than the mean shift algorithm" and becomes the bottleneck: https://scikit-learn.org/stable/modules/generated/sklearn.cluster.MeanShift.html

## Implications for the design
- Structure the fit as variable projection, not one monolithic nonlinear least squares: an outer `scipy.optimize.least_squares` (dense Jacobian, `trf`, robust `loss='soft_l1'` or `'huber'`, bounded light directions/colours) over roughly 8 slots x a handful of params each — comfortably inside "not very large" dense-solver territory — and an inner closed-form linear solve per palette entry (`lsq_linear` with bounds, or `nnls`) for the albedo-ish scalars given the current light estimate, vectorized in numpy across all 10^5-10^6 entries rather than looped through `least_squares` per entry.
- Reserve PyTorch for the case where the vectorized numpy inner loop (or the outer iteration count times entry count) is too slow on CPU: batch the per-entry linear systems as tensors, solve with `torch.linalg.lstsq` on CPU (for rank-deficiency safety) or fall back to Adam/LBFGS on GPU for a differentiable robust-loss formulation. A 12 GB GPU comfortably holds batches on the order of 10^6 entries x 8 slots x small per-entry float32 arrays (tens of MB), so VRAM is not the binding constraint — CUDA's `gels`-only `lstsq` driver and its full-rank assumption is the actual gotcha to design around.
- For the point-light clustering step, default to `sklearn.cluster.HDBSCAN` over hand-tuned-`eps` DBSCAN, since effect-slot N·L/r² residual clusters are likely to vary in density across a level; keep MeanShift only as a fallback for levels with few enough residual samples that its worse high-dimensional scaling and slow `estimate_bandwidth` step don't matter.
- Keep the dependency surface to scipy + numpy + scikit-learn + (optional) PyTorch; no need for JAX, ceres/theseus bindings for this problem size and offline, single-machine workflow.

## Follow-ups
- Benchmark the vectorized numpy `lsq_linear`/`nnls` inner loop against a PyTorch CPU/GPU batched `lstsq` on a representative palette size (10^5-10^6 entries) to decide whether the PyTorch fallback is actually needed, or if numpy alone is fast enough.
- If PyTorch is adopted, write the exact `uv` `[[tool.uv.index]]` / `[tool.uv.sources]` pin for the target CUDA version once the workstation's driver/CUDA version is confirmed, rather than relying on `--torch-backend=auto` at install time.
- Prototype HDBSCAN vs DBSCAN on one level's actual effect-slot residual point cloud to confirm HDBSCAN's density-robustness benefit holds for this specific data before committing to it as the default.
